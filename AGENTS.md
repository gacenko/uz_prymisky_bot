# uz_prymisky_bot — контекст для AI-агентів

## Мета проекту
Моніторинг публічного Telegram-каналу [@UZprymisky](https://t.me/s/UZprymisky)
(Укрзалізниця, приміські поїзди), фільтрація постів про затримки/скасування/
відновлення руху для конкретного маршруту (Ніжин – Київ, дільниця Княжичі →
Березняки — щоденний маршрут члена сім'ї з Броварів на роботу в Київ), і
надсилання стислих сповіщень у сімейний Telegram-чат.

Повна архітектура, покрокове налаштування і опис фільтра — у
[README.md](README.md). Цей файл — контекст і угоди для агента, що працює
над кодом, не дублює README.

## Ключові рішення і чому

### Тригер — Cloudflare Worker, не GitHub Actions `schedule:`
Емпірично підтверджено (два реальні прогони): нативний `schedule:` у GitHub
Actions на цьому акаунті відкладає часті scheduled-запуски на 2+ години
замість заявлених 5 хвилин. Замість цього `worker/worker.js` (Cron Trigger,
`*/10 * * * *`) робить `workflow_dispatch` через GitHub API —
`workflow_dispatch`/`repository_dispatch` виконуються GitHub миттєво, бо це
вхідна подія, а не крон-черга. Той самий принцип, що й у `running_sync`
(Strava webhook → Cloudflare Worker → repository_dispatch), тільки тут немає
зовнішнього вебхука-джерела, тому таймер — сам Worker.

**⚠️ Поточний стан (2026-09-15): Cron Trigger на Cloudflare не спрацьовує.**
Підтверджено діагностикою: 0 інвокацій навіть на щойно створеному Worker'і
(`uz-prymisky-cron-v2`) з cron раз на хвилину — проблема на рівні акаунту
Cloudflare (ймовірно залишок інциденту "Workers Cron Triggers degraded",
9-12 вересня 2026, офіційно "Resolved", але не для цього акаунту). Через це
в `check.yml` тимчасово повернутий `schedule: */10 * * * *` як запасний
варіант (працює з непередбачуваними затримками, як описано вище, але краще
ніж нічого). **Коли Cloudflare полагодить Cron Trigger — прибрати
`schedule:` з check.yml**, лишити тільки `repository_dispatch`/
`workflow_dispatch`.

### Репозиторій має бути публічним
Часті запуски (`*/10 * * * *`) на приватному репо можуть вичерпати
безкоштовний ліміт GitHub Actions (2000 хв/міс) і почати коштувати гроші.
Публічний репо — безлімітні безкоштовні Actions-хвилини. У коді немає
секретів (токени лежать окремо в GitHub Secrets), тож публічність безпечна.

### Userbot (Telethon), а не тільки звичайний бот
Bot API отримує пости з каналу лише якщо бот — адмін цього каналу. Зробити
свого бота адміном офіційного каналу УЗ неможливо. Тому: **читання** каналу
— через Telethon під особистим акаунтом власника; **відправка** у сімейний
чат — через звичайного бота (BotFather) з Bot API, бо там власник вже
адмін/учасник.

### Один пост може містити кілька поїздів
Типовий формат УЗ під час тривог: один пост, кілька рядків "Поїзд №...
курсує...". `build_delay_blocks()` у `scripts/check_channel.py` розбирає
кожне речення окремо через `finditer`. **Був реальний production-баг**: код
раніше брав перший збіг регулярки (`.search()`) на весь текст, тоді як
релевантність перевірялась по всьому тексту — тому повідомлення про
нерелевантний поїзд №6902, згаданий першим у пості, витісняло дані
релевантного №6911, згаданого другим. Якщо чіпаєш цю логіку — тримай у
голові, що вхідний текст завжди може містити кілька незалежних "Поїзд
№..." речень.

### Відсічка 09:00 (`CUTOFF_TIME`)
Сповіщення про затримку шлеться, лише якщо перерахований час відправлення з
Княжичів ≥ 9:00. Дрібні затримки на ранніх поїздах, які все одно
встигають до 9-ти, не варті сповіщення. Стосується лише категорії "delay"
(є конкретний розрахунок часу); скасування/відновлення шлються завжди.

### `TRAIN_SCHEDULE` — статичний словник, не з API
Розклад приміських поїздів УЗ не має публічного API для програмного
запиту, тому час відправлення/прибуття для дільниці Княжичі → Березняки
захардкоджений у словнику (`scripts/check_channel.py`). Чинний на
2026-06-28..2026-12-12 — після зміни сезонного розкладу треба оновити
вручну (звірити з розкладом на сайті УЗ).

## Конвенції коду
- **Коментарі й докстрінги в коді (.py, .js) — англійською.** README.md і
  AGENTS.md — українською (робоча мова власника проекту й UZ-специфічна
  термінологія в даних).
- Без зайвого логування "про всяк випадок" (`console.log`, verbose print) —
  тільки те, що реально потрібно для діагностики в GitHub Actions
  логах/Cloudflare dashboard.
- Немає тестового фреймворку в репо — зміни в `classify()`/
  `build_delay_blocks()`/`add_minutes()` перевіряються ad hoc скриптом
  (імпорт модуля з підставними env-змінними, прогін прикладів реальних
  постів каналу). Регресій вартує перевіряти саме на реальних форматах
  постів (є приклади в git history), а не тільки синтетичних.

## Важливі файли
```
scripts/
  check_channel.py     — основна логіка: фільтр, парсинг, форматування, відправка
  generate_session.py  — одноразовий локальний скрипт для TG_SESSION (не в CI)
worker/
  worker.js             — Cloudflare Worker, Cron Trigger → workflow_dispatch
  wrangler.jsonc         — конфіг Worker'а (GITHUB_OWNER/REPO, crons)
.github/workflows/
  check.yml              — job, що виконує check_channel.py (repository/workflow_dispatch)
state/
  last_message_id.txt    — id останнього обробленого поста (коміститься воркфлоу)
```

## Деплой
Worker деплоїться вручну (`cd worker && npx wrangler deploy`), не
автоматично з git — так само як `running_sync/worker`.
